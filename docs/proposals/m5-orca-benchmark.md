## 2. 이번 시험에서 드러난 문제와 Orca의 답

- 11-17~18 todo 시험의 실패 대부분은 **엄격한 이벤트 해석** 때문이었다.
  - Codex 내장 도구(`mcpToolCall`), 웹 검색(`webSearch`), 읽기 전용 실행의 명령 승인 요청(`item/commandExecution/requestApproval`)이 올 때마다 실행이 멈췄다.
  - 그때마다 그 기능을 끄는 식으로 대응했다(144f5601, eb05b6af). 사용자가 원하는 방향과 반대다.
- Orca는 모르는 것을 무시하고 상태만 본다. 권한은 처음에 정하고 그다음은 에이전트에게 맡긴다.
- 변경 화면이 읽기 힘들었던 것도 자체 diff 형식 때문이었다. Orca는 git이 이미 아는 변경을 그대로 보여 준다.

## 3. 제안 — 무엇을 가져올지

### 3.1 에이전트 실행과 권한 (먼저)

1. **권한 모드를 Orca 채팅 경로처럼 넷으로**: 묻기 / 편집만 자동 / 알아서(자동 판단) / 전부 허용. 새 프로젝트 기본값은 "전부 허용"으로 하고 첫 작업 때 한 번 확인받는다.
2. **허용 범위 안의 도구는 끄지 않는다**: 웹 검색, 명령의 인터넷 접속, 브라우저·computer use를 권한 항목으로 둔다. 허용하면 쓰게 하고, 실행 기록에 "웹 검색: 검색어"처럼 보여 준다.
3. **이벤트 해석을 관대하게**: 모르는 항목·알림은 실행을 멈추지 않고 "기타 작업"으로 기록한다.
   - 승인 요청은 지금 권한 모드로 판단한다. 판단할 수 없으면 사람에게 올린다.
   - 실행을 멈추는 경우는 프로토콜이 깨졌을 때(형식 오류, 순서 위반)만이다.
4. **사람에게 올리기**: 팀원이 권한·질문으로 막히면 총괄을 거쳐 사용자에게 쉬운 말 카드로 묻는다(결정 게이트). 총괄이 대신 허용하는 것은 기본으로 끈다.
5. **위임 회수 계약**: 위임마다 작업 id와 시도 id를 붙인다. 완료 보고는 실패해도 정확히 한 번 받는다. 낡은 재시도의 결과가 섞이지 않는다.

### 3.2 워크트리

1. **사용자 저장소의 실제 git worktree + 실제 브랜치**로 바꾼다. 작업 하나에 브랜치 하나(`elsecrew/<작업 이름>`)를 쓴다.
   - 위치는 Orca처럼 홈 아래 앱 폴더(예: `~/elsecrew/workspaces/<프로젝트>/<작업>`)나 지금처럼 앱 데이터 폴더로 한다.
2. 팀원 단계가 끝날 때마다 그 브랜치에 **자동 커밋**한다(메시지는 단계 요약). 사용자는 git을 몰라도 되고, 기록과 되돌리기는 git이 한다.
3. **"내 폴더에 반영" = 그 브랜치를 사용자의 현재 브랜치에 합치기**로 바꾼다. 사용자가 고른 "최신 우선"에 맞춰, 충돌 나는 파일은 작업 쪽을 택한다.
   - 사용자 폴더에 커밋하지 않은 수정이 있으면 반영 전에 알린다.
   - 개발자 사용자를 위해 "브랜치로 두기 / PR 만들기"를 선택지로 둔다.
4. 작업을 지워도 병합 안 된 브랜치는 남긴다(Orca 규칙).
5. 셋업 스크립트(`npm install` 등)는 작업 공간을 만든 뒤 백그라운드로 돌리고, 끝날 때까지 첫 에이전트가 기다리게 한다.

### 3.3 변경 파일 관리 (GitLens/Orca식)

1. 변경 목록은 git 상태 그대로 보여 준다. 기준 브랜치 대비 커밋된 변경과 작업 중인 변경을 나누고, 커밋(=팀원 단계)별로도 볼 수 있게 한다.
2. 비교는 git diff 기반 Monaco 나란히 비교로 한다(지금의 전체 파일 교체 diff 복원은 없앤다).
3. **메모 모아 보내기**: 비교 화면의 줄마다 "여기 이렇게"를 적고 총괄에게 한 번에 보낸다(Orca Annotate AI Diff).
4. 에이전트가 쓴 줄 표시(Attribution)는 나중에 검토한다.

### 3.4 상태·알림 (작게 바로 가능)

- 작업 상태를 작업 중 / **확인 필요** / 완료 / 실패 / 쉬는 중 다섯으로 나눈다. 색은 "확인 필요"에만 강하게 쓴다.
- 작업이 끝나거나 막히면 시스템 알림을 띄운다. 사용량 80% 경고와 리셋 시각을 보여 준다.

## 4. 기존 원칙과 부딪히는 점 — 사용자 결정 필요

| 기존 원칙(CLAUDE.md 등) | Orca 방식 | 결정할 것 |
| --- | --- | --- |
| 원본 보호: 원본은 사용자가 명시적으로 반영할 때만 바뀐다 | 실제 worktree·브랜치를 사용자 저장소에 만든다(원본 작업 폴더는 그대로, `.git`에 브랜치·worktree 기록이 생김) | 사용자 저장소에 브랜치를 만들어도 되는가 |
| 안전 기본값 우선, 감독 못 하는 도구는 끔 | 기본 full-access, 모르는 이벤트 무시 | 기본 권한 모드, fail-closed를 어디까지 풀지 |
| 앱 전용 로그인, 기존 설정 파일을 덮어쓰지 않음 | 기존 `~/.claude`·`~/.codex` 로그인 재사용, 홈에 hook 설치 | 앱 전용 로그인을 유지할지(유지 권장: hook은 앱 전용 프로필 안에 둘 수 있다) |
| 비개발자 대상: git 용어를 숨김 | 개발자 UI(브랜치·커밋·PR·3-way) | git은 뒤에서만 쓰고 화면 말은 지금처럼 쉬운 말로(권장) |

- 조사 에이전트는 Orca의 "워크트리 = 샌드박스" 가정이 실제 격리(파일·네트워크)가 아니라는 점을 짚었다.
- `sharedDirectories` 링크(작업 공간 수정이 원본으로 새는 구조)와 `.env` 복사는 가져오지 않는 것을 권한다.
